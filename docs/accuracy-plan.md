# 准确率:从 59 到 82 的实验记录

dev100,抽取 v3-detail,读者 gpt-4.1-mini(strict prompt),判分 GPT-4o,不合并。准确率按全部 100 题算(含 6 道"无法回答"题);早期记录里的 57% 是只算 94 道可答题的口径,同一次 run 的 100 题口径是 59。判分同一答案两次可差 ±2 题,4 题以内不作结论。最终结果汇总在 `docs/results.md`,本文是过程。

## 1. 上限

把标注的证据会话**原文**直接给 gpt-4.1-mini(oracle 基线):**84/100**。oracle 也答错 16 题(multi-session 7、temporal 4、preference 2…),那是读者本身的上限。80% 在这个读者下够得着。

## 2. 40 道失败题逐题归因(只事实 59 那版)

| 阶段 | 题数 | 说明 |
|---|---|---|
| 抽取没抽到 | 14 | 7 题答案在**助手**轮(推荐的餐馆、店名、视频名);5 题是用户长轮里的顺带一提("by the way I got to attend … at the Episcopal Church") |
| 答案要跨会话数数/加总 | 13 | "3 次""$495""five items":证据会话全都在上下文里,但每个会话只剩一两条 15 词的改写,数不出来 |
| 在上下文里,读者答错/弃答 | 10 | 多数是改写丢了细节(金额、时长、序数) |
| 抽到了没存住 / 存了没检索到 / 检索到没打包 | 1 / 1 / 1 | 存储不限时读侧几乎不丢 |

关键数字:40 道失败题涉及 80 个证据会话,**80 个都有条目进了读者上下文**。"存活证据只有 30-50% 被注入"是按条目算的,按会话算覆盖是 100%。问题不是没检索到,是**送到读者面前的是 72 条、每条 15 个词的改写,而不是原文**。

## 3. 读侧实验:事实做索引,原文做载荷

检索不变(事实/情节 → BM25 ⊕ dense → 打包),再把打包条目对应的原文轮(来源轮 ±1)按相关度加进上下文。全部读侧,ingest 走缓存,一轮 100 题几分钟。这一轮的原文直接取自题目自带的对话,等于系统旁边挂了一份不限量的原始日志,只用来定位损失,不是设计。

| 读者看到的 | 总体 | KU | multi | SS-asst | SS-pref | SS-user | temporal |
|---|---|---|---|---|---|---|---|
| 只有事实 | 58 | 12/15 | 9/24 | 4/11 | 1/6 | 8/13 | 19/25 |
| 事实 + 原文轮 4k | **71** | 13/15 | 11/24 | 7/11 | 3/6 | 12/13 | 19/25 |
| 事实 + 原文轮 8k | 70 | 13/15 | 11/24 | 8/11 | 3/6 | 11/13 | 19/25 |
| 只有原文轮 8k | 59 | 11/15 | 9/24 | 8/11 | 2/6 | 11/13 | 13/25 |
| 事实 + 整会话 8k | 70 | 13/15 | 8/24 | 11/11 | 2/6 | 11/13 | 20/25 |
| oracle | 84 | 14/15 | 17/24 | 11/11 | 4/6 | 12/13 | 21/25 |

- +13 来自让读者看原文;4k 原文预算够,8k 不涨。
- 事实和原文互补:只给原文 temporal 掉到 13/25(事实带有效期窗口,原文没有);只给事实 SS-assistant 4/11。
- 整会话让 SS-assistant 满分但挤掉 multi-session(8k 只装得下三四个会话),轮级粒度是对的。

外部对照(`docs/memory-systems-survey.md`):LongMemEval 上 80% 以上的系统都让读者看原文轮、抽取的事实只做检索键;不索引助手轮的系统 SS-assistant 都在 71-73;LLM 查询分解、换更强读者、继续雕抽取措辞都不值得做。

## 4. 落地第一步:原文进存储,读侧按来源轮扩展

每轮原话随事实一起存(当时不计预算),读侧打包后按来源轮 ±1 填 `budget.raw_tokens`。

| | 只事实 | 原文 4k,每会话先保一轮 | 原文 4k,纯按分 |
|---|---|---|---|
| 总体 | 59 | 65 | **71** |
| multi-session | 10/24 | 10/24 | 13/24 |
| single-session-assistant | 4/11 | 6/11 | 7/11 |
| single-session-preference | 1/6 | 4/6 | 2/6 |
| single-session-user | 8/13 | 11/13 | 12/13 |
| knowledge-update | 12/15 | 12/15 | 13/15 |
| temporal | 19/25 | 18/25 | 19/25 |

和第 3 节的实验一致。"每个会话先保一轮"(`read.raw_diversity`)少 6 题:它把高分会话的相邻轮挤出 4k 预算,默认关。读者每题看约 1.1k token 事实 + 4k token 原文。

## 5. 第二步:原文轮做检索单元

轮文本做向量,轮文本 + 该轮抽出的事实做 BM25(`read.k_turns=30`);直接检索到的轮和事实带出的轮合并打分后填原文预算。

| | 只事实 | 原文 4k | + 轮索引 4k | + 轮索引 **6k** | + 轮索引 4k,直检权重 0.5 | + 轮索引 8k |
|---|---|---|---|---|---|---|
| 总体 | 59 | 71 | 73 | **77** | 66 | 75 |
| single-session-assistant | 4/11 | 7/11 | 11/11 | 11/11 | 8/11 | 11/11 |
| single-session-user | 8/13 | 12/13 | 10/13 | 12/13 | 11/13 | 12/13 |
| single-session-preference | 1/6 | 2/6 | 4/6 | 3/6 | 2/6 | 2/6 |
| multi-session | 10/24 | 13/24 | 11/24 | 12/24 | 9/24 | 14/24 |
| knowledge-update | 12/15 | 13/15 | 14/15 | 15/15 | 14/15 | 14/15 |
| temporal | 19/25 | 19/25 | 18/25 | 19/25 | 17/25 | 18/25 |

- 轮索引把助手内容类题全部追回(4 → 11),KU 到 15/15。4k 预算下直检轮和事实带出的轮抢位子(user、multi 各掉 2),6k 解决;8k 在噪声内。
- 直检权重减半最差:高分的直检轮被压到预算外。
- 读者 prompt 两版(逐条摘记再作答、冲突取最新、相对时间按原文日期解释)都是 69:计数题涨 1,temporal 掉 2-4,不采用。

## 6. 原文计入预算 B

用户的决定:原话必须占存储预算。三个设计依次在 dev100 上验证:

| 设计 | 结果 | 为什么不行 |
|---|---|---|
| 原话免过 sieve 密度门槛,满了再按增益置换 | B=0.015:15 | 原话先到先得,占掉三分之二预算,事实被挤没 |
| 原话作为普通覆盖目标和候选 | 不限:65-70;B=0.015:17 | 六个词的泛泛问句是最便宜的自覆盖项,预算里存的是废话;给长度加权后又偏向 500 token 的助手长篇,并把 sieve 归一化基准抬到 140,证据所在的短用户轮被拒 |
| **二级条目(最终)** | 不限:76;曲线见下 | 事实的选择和只事实时逐条一致(原话不做覆盖目标、不进归一化、不计 Hawkes 提及,已用集合相等验证);原话按 `具体性 × 说话人 / max(token, 20)` 用剩余预算,预算紧时先淘汰,永远不挤事实 |

覆盖目标不适合给原话定价:它衡量"是否已被相似内容代表",而原话的价值是"细节没被改写"。

同一时期发现 `configs/raw_turns.yaml` 的 `extends: default.yaml` 之前不生效(配置系统没有这个功能,该键被忽略),没写的字段静默回落到代码默认值:向量模型 hash、抽取器启发式、判分 gpt-4.1-mini、sieve 门槛 0。用它跑的第一轮预算曲线作废;实现真正的继承(带测试)后重跑。

dev100 曲线(gpt-4.1-mini 读,gpt-4o 判):

| B | 预算 tok | swap | fifo | lru | 原文进上下文 |
|---|---|---|---|---|---|
| 0.015 | 1.5k | **34** | 30 | 23 | 0 |
| 0.03 | 3.1k | **46** | 31 | | 0 |
| 0.06 | 6.2k | **49** | | | 0 |
| 0.125 | 12.9k | **60** | 60 | | 2.1k |
| 0.25 | 25.8k | **72** | | | 6k |
| 不限 | 113k | **76** | | | 6k |

- B ≤ 0.06:预算全被事实用掉,原话一条不剩,数字等于只事实系统(0.015 时只事实也是 34);swap 对 fifo 的差距在 0.03 最大。
- 0.125:事实全存下(约 9k),余量给原话;swap 和 fifo 相同是因为事实没被淘汰过。
- 证据存活/注入两个指标的分母现在含原话候选,和只事实的旧数不可直接比。
- 为什么小预算这么低:可答题的证据原文中位只有 138 token,1.5k 预算装得下 88/94 题的证据。差的不是空间,是写入时不知道将来问什么;覆盖目标留的是"每个话题一条代表",评测问的是针尖。这是写入价值函数的问题,没有动。

## 7. held-out:test 200 题

`configs/raw_turns.yaml`,存储不限,dev 上所有参数选择都没看过这批题。子集按类型分层抽样(`data/test200_seed0.json`,197 题)。抽取 8510 场唯一会话 9.5 小时,预热 1.2 小时,评测 1 小时。

| | test200 | dev100 |
|---|---|---|
| **总体** | **161/197 = 0.82** | 0.76 |
| knowledge-update | 27/28 | 14/15 |
| single-session-user | 24/26 | 12/13 |
| single-session-assistant | 21/22 | 11/11 |
| temporal-reasoning | 41/51 | 19/25 |
| multi-session | 34/48 | 13/24 |

held-out 没有掉。test200 的预算曲线(0.22 / 0.35 / 0.60 / 0.78 / 0.82)和 297 题合并的曲线在 `docs/results.md` 第 6 节。

## 8. 运维上碰到的

- 六个分片并行打满 OpenAI 每分钟 20 万 token 限额,429 单独给 20 轮退避。
- GPU 与 vLLM 共享时,向量模型输入封顶 2048 token、批次 8;NLI 模型放 CPU(它只服务已关闭的合并步骤)。
- 链式脚本要检查上一步的退出码,否则预热失败后评测会在 CPU 上爬几个小时。
